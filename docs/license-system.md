# 签到授权（白名单）体系

> 需求：**别人把姓名 + 学号给你，你才给他开放优学院签到功能**
> 方案：远程名单 JSON + 有效期 + 只控签到模块 + 使用日志

---

## 一、怎么工作

```
你（管理员）维护一个名单 JSON，放在任意 HTTPS 直链上
        ↓
用户 App 启动 / 点「刷新授权」时拉取名单
        ↓
拿用户已绑定的学号去名单里查
        ↓
查到且未过期 → 解锁签到模块
没查到 / 过期 / 被禁用 → 显示授权说明页（并给出开通指引）
```

**改名单不用重新打包 App** —— 用户下次打开或点刷新就生效。

---

## 二、名单格式

```json
{
  "version": 3,
  "issuedAt": 1791302400000,
  "entries": [
    {
      "name": "同学A",
      "studentId": "2099000000116",
      "expiresAt": 1793894400000,
      "note": "同班同学"
    },
    {
      "name": "王五",
      "studentId": "2099000000155"
    },
    {
      "name": "李四",
      "studentId": "2099000000177",
      "disabled": true
    }
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `version` | 是 | 名单版本号，便于排查 |
| `issuedAt` | 是 | 名单生成时间（毫秒时间戳） |
| `entries[].name` | 是 | 姓名（用于你核对） |
| `entries[].studentId` | 是 | 学号（匹配时**忽略大小写与首尾空格**） |
| `entries[].expiresAt` | 否 | 到期时间戳；**不填 = 永久有效** |
| `entries[].disabled` | 否 | 单独停用，**优先级高于有效期** |
| `entries[].note` | 否 | 备注，只有你能看到 |
| `sig` | 否 | 预留签名位（见下方安全说明） |

**判定顺序**：未绑定 → 无名单 → 不在名单 → 被停用 → 已过期 → **通过**

## 三、配置 App

在 `.env` 里配置名单地址：

```bash
EXPO_PUBLIC_LICENSE_URL=https://你的地址/whitelist.json
```

**放哪里？** 任意支持 HTTPS 直链的地方都行：

| 方式 | 说明 |
|---|---|
| 对象存储（阿里 OSS / 腾讯 COS） | 设成公开读，拿到直链即可 |
| GitHub Gist（raw 直链） | 免费、方便改；注意别放敏感信息 |
| 私有 CDN / 你的网盘直链 | 只要 App 能 fetch 到就行 |

> 未配置该变量时：**开发模式（`__DEV__`）自动旁路**，方便本地调试；生产构建则视为未授权。

## 四、你最常用的两个操作

### 加人

编辑名单 JSON，在 `entries` 里加一条，保存 → 告诉对方"点一下刷新授权"。

```json
{ "name": "新同学", "studentId": "2025404030200", "expiresAt": 1793894400000 }
```

### 踢人（两种）

```json
// 方式一：停用（保留记录）
{ "name": "某同学", "studentId": "2025404030200", "disabled": true }

// 方式二：直接删掉这一条
```

对方下次刷新就会看到「授权已停用」或「未授权」。

### 批量续期

把 `expiresAt` 统一改成一个新时间戳即可。时间戳换算：

```
2027-01-01 00:00:00 (UTC+8) = 1798732800000
```

## 五、用户侧看到什么

| 状态 | 界面显示 |
|---|---|
| 未授权 | 签到模块上锁 🔒 + 「未授权」；点进去是**开通指引页**（含「复制申请信息」按钮，一键把姓名学号发给你） |
| 待同步 | 「暂时无法校验，请联网后重试」+ 刷新按钮 |
| 已过期 | 「授权已于 2026-11-01 到期」+ 提示联系管理员续期 |
| 已停用 | 「该账号的授权已被停用」 |
| 已授权 | 正常使用，卡片上显示到期日 |

**关键**：未授权时**不是报错**，而是展示说明页和开通步骤 —— 用户知道该做什么。

## 六、边界与风险（必须知道）

### 这个方案的防护强度

| 能防 | 不能防 |
|---|---|
| ✅ 普通用户（没过名单就用不了） | ❌ **会反编译的人** —— 名单是本地校验，改 APK 或伪造本地存储就能绕过 |
| ✅ 名单被误改（格式校验会拦） | ❌ 中间人替换名单（除非启用签名，且密钥不进 APK） |
| ✅ 到期自动失效 | ❌ 离线长期使用（缓存的名单 24 小时后需要联网重新校验） |

**一句话**：**防君子不防小人**。目标是挡住普通用户，不是对抗逆向者。
真要防绕过，必须把校验放到服务端 —— 那就回到"要建服务器"那条路。

### 规模化使用的风险（你之前选了"十几到几十人"）

| 风险 | 说明 |
|---|---|
| **优学院风控** | 多个学号从同一出口 IP 高频签到，容易被识别为"代签服务"，**可能牵连所有授权用户** |
| **你自己的身份** | 你成了"组织代签"的人，性质和个人使用不同 |
| **凭据安全** | 用户把学号密码存在自己手机上；但一旦你要求他们发给你，责任就转到你这边 |
| **建议** | ① 控制人数 ② 不要统一时间签到（App 已有抖动与随机延迟） ③ 不要收费 ④ 只给认识的人 |

### 代码里已做的保护

- 每个用户**独立会话**，互不共享
- 轮询有 **±30% 抖动 + 随机提交延迟**，避免同一时刻集体提交
- **单账号串行提交**、单日上限、限流退避、连续 3 次熔断
- **夜间静默**
- 使用日志留痕（谁、什么时候、做了什么）

## 七、使用日志

App 会记录（本地）：

| action | 触发时机 |
|---|---|
| `license-check` | 每次拉取名单并校验 |
| `checkin` | 自动签到 |
| `manual-checkin` | 手动签到 |
| `unbind` | 解绑优学院账号 |

日志字段：时间、学号、动作、详情、成功与否。目前存在**用户本机**，用于自查与反馈。
如需汇总到你那边，得接服务端上报 —— 那又回到"要服务器"。

## 八、测试

```bash
npm run test:license
```

**29 个用例**覆盖：

- 名单命中 / 不在名单 / 已过期 / 被停用 / 永久有效
- **边界**：到期时刻本身仍有效（`now > expiresAt` 才失效）
- 学号匹配忽略大小写与首尾空格
- 未绑定 / 无名单 / 缓存过期 / 开发旁路
- 名单格式校验（entries 非数组、缺 studentId、空学号、缺 name、非对象）
- **模块联动**：未授权时签到模块**仍显示但不可用**；**不影响外卖/待办**；用户手动关闭优先；iOS 上外卖仍按平台过滤
