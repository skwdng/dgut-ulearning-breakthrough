## 4. 部署方式

仓库里的脚本（`D:\skwdngapp\server\`，本地）负责把代码推上去：

| 脚本 | 作用 |
|---|---|
| `install-vps.sh` | 首次安装 / 全量部署（含 systemd 单元、目录、依赖） |
| `update-vps.sh` | 更新 `server.cjs` 并重启 `lifekit`（**最常用**） |
| `deploy-ai.sh` / `update-ai-on-vps.sh` | 部署 / 更新小c 服务（8789） |
| `setup-ollama.sh` / `fix-ollama-*.sh` | Ollama 安装与镜像/服务修复（历史脚本，见第 9 节） |

典型更新流程（在本地仓库执行）：

```bash
# 1) 服务端代码
scp server/server.cjs root@120.24.204.138:/opt/lifekit/
ssh root@120.24.204.138 "systemctl restart lifekit"

# 2) APK（正式版 / 测试版）
scp server/apk/lifekit-latest.apk server/apk/version.json \
    root@120.24.204.138:/opt/lifekit/apk/
scp server/apk/lifekit-test.apk server/apk/version-test.json \
    root@120.24.204.138:/opt/lifekit/apk/

# 3) 验证
curl -s http://120.24.204.138:8787/api/version
curl -s "http://120.24.204.138:8787/api/version?ch=test"
```

⚠️ `server.cjs` 部署前会留 `server.cjs.bak-<时间戳>`，出问题直接 `cp` 回去重启即可。

## 6. 数据与日志

**`data.json`（真实数据，最敏感）**
- 用户列表：学号、设备、授权状态、登录记录
- 授权码只存哈希
- 结构改动会影响 `/admin` 和 App 授权判断，改前先备份

**`client-errors.log`（JSON Lines，一行一条）**
- 字段：`at` / `ip` / `app` / `version` / `versionCode` / `stage` / `message` / `stack` / `extra`
- `stage` 取值：`entry` / `app_module_loaded` / `shell_mounted` / `ready` / `prev_startup_unfinished` / `native_crash`
- 典型查询：

```bash
# 最近 20 条
tail -20 /opt/lifekit/client-errors.log

# 只看崩溃
grep native_crash /opt/lifekit/client-errors.log | tail -5

# 按版本统计启动打点
grep -o '"version":"[^"]*"' /opt/lifekit/client-errors.log | sort | uniq -c | sort -rn
```

## 9. 已知坑（重要，别重踩）

1. **内存只有 1.6G**
   小c 只能用 `qwen2.5:0.5b`；换 4B 以上模型会 OOM。跑 `ollama` 时不要再并行跑构建。

2. **`client-errors.log` 会一直长**
   没有轮转，必要时手工截断（先 `cp` 备份）。里面含用户 IP，别外传。

3. **`server.cjs` 是单文件大程序（约 65KB）**
   改它之前一定先备份；`update-vps.sh` 每次部署会自动留 `.bak`。

4. **APK 分发靠 `version.json`**
   `/api/version` 返回的 `available`、`version`、`versionCode`、`url` 都来自这个文件；改版本时**两个文件必须一起传**，否则 App 会拿到旧版本号。

5. **8789 只监听 127.0.0.1**
   外部访问小c 必须走 `http://<IP>:8787/ai`，直连 8789 不通。

6. **Ollama 历史上有镜像/服务脚本问题**
   `fix-ollama-mirror.sh`、`fix-ollama-runner*.sh`、`fix-ollama-service.sh` 都是当时踩坑写的修复脚本，重装 Ollama 前先看看。

7. **App 崩溃排查路径**
   先 `grep native_crash` 看有没有栈；`prev_startup_unfinished` 表示上次启动没走完（可能是被系统杀）。Java 未捕获异常会写盘并在下次启动上报。

8. **不要在服务器上直接改 App 相关逻辑**
   业务逻辑都在 App 侧（GitHub: `skwdng/dgut-ulearning-breakthrough`），服务器只管版本分发、授权、上报、以及小c。

### 12.5 资源约束（别踩）

- `siyige.service` 里写了 `MemoryMax=700M`，超了会被 systemd 杀 → `journalctl -u siyige` 会看到 `oom-kill`
- 启动参数固定为 `-Xmx384m -XX:MaxMetaspaceSize=128m -XX:+UseSerialGC`，**不要调大**，1.6G 的机器留不出更多
- H2 是文件模式，**别再起第二个实例指向同一个 data 目录**（会锁表）
- 服务器上 `time-scale=1.0`（真实时长）；本机演示用的是 0.02，别搞混


### 12.6 多人同时使用（2026-11-01 补充）

- 前端每个浏览器生成独立 `sy_uid`（localStorage），所有接口带这个 id；
  此前写死 `u1` 导致所有人的记录混在一起，**已修**。
- 实测（本机加速模式）：
  - alice 打完一场 → 记录 1 条；bob 打完 → 记录 1 条；nobody → 0 条，互不可见
  - 房间模式两人可同时入座对打（SY-XXXX，真人 A1/A2 + 6 个 AI）
- **没有登录鉴权**：任何拿到 URL 的人都能用，身份靠浏览器本地 id。
  要做到"账号级"隔离，需要加注册/登录 + JWT（规格里 M1 有，尚未实现）。
